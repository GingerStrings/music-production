# 公开与维护

公开包只包含 skill、原创工具、说明和合成数据示例。个人工程和商业音源资料保留在仓库外或被忽略的工作目录。

## 提交前检查

检查实际待提交文件和历史，而不只依赖 `.gitignore`：

- 不包含用户 CPR/FLP、采样、音频、插件程序、商业预置或厂商 KSP。
- 不包含 `audioComponent`/`editController` 的实际状态字节、Bank 转储、NKI 解码数据、引擎派生表或激活信息。
- 不包含个人路径、用户名称、机器标识、库清单、音源定位报告、私有模板哈希或本地测试输出。
- 不包含 API token、`.env`、缓存、压缩的私有素材或整个工作区的打包文件。
- 外部引用说明来源；新增第三方代码遵循对应许可证。当前仓库 MIT 草案只涉及原创内容。

示例中的虚构延迟必须保持示例身份。不要把某一次作品的音乐结构、调性、技法或编制升级为 skill 的默认艺术要求。

## 发布方法

先运行测试并检查 `git status`、`git diff --cached` 和实际文件清单。准备好 GitHub 仓库目标、许可和介绍后，再按用户明确的发布意图创建或推送远端仓库。

在目标仓库已确定的本地检出中，可以按常规 Git 工作流提交和推送。未确定账号、仓库或可见性时，先交付可检查的目录/ZIP；不猜测远端，也不替用户公开整个原始工程目录。

首次发布前可调整本地 MIT 草案。已经公开的版本及其他贡献者内容可能涉及既有授权，后续更改须逐项处理。

## 维护原则

将新 Cubase 版本和新的模板结构视为需要验证的适配对象。保留最小合成回归案例与真实项目的私有验证记录，公开报告只描述验证范围。

艺术上的建议在当次创作中讨论；技术规则应说明它所保护的具体不变量。例如“命令 CC 不插值”保护奏法选择，“所有作品必须采用某曲式”不属于本 skill 的职责。
