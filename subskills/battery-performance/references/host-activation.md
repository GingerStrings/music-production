# 复制轨道后的宿主停用故障

## 克隆实例的启用标记

克隆停用的 Battery 插件槽时，目标实例可能继承停用标记。若新实例能显示鼓组和采样，但在 Cubase 播放时没有电平，可先检查宿主保存的启用状态。

在检查工具支持的 CPR 结构中，`Synth Slot → Plugin → Active` 是类型为 1 的整数。0 表示停用，1 表示启用。需要修复时，仅对目标实例设置 Active=1 并回读保存结果。

后续构建明确设置新实例的预期启用状态，不仅替换 audioComponent。已有工程的有意停用轨道继续保留；修复另写新 CPR，不自动批量激活所有插件。使用命名属性读写器及匹配的 archive 重建流程，保留实例身份与路由，勿按未知文件中的固定字节位置补丁。

这条修复针对已确认的停用原因。采样可见与后台有声均不足以判定宿主槽已启用，Active=1 也不能单独证明音频链已打通。

## 只读检查工具

[check_host_activation.py](../scripts/check_host_activation.py) 读取父 skill 已支持的 RIF2 / 乐器轨属性。它按已观察到的 Battery 4 UID 识别目标，不依赖可重命名的轨名或 Plugin Name。其他 UID 可在确认插件身份后用 `--plugin-uid` 明确指定；未识别实例会列在 skipped 中，不能据此宣称所有 Battery 版本都已检查。

在仓库根目录运行以下命令。

```bash
python subskills/battery-performance/scripts/check_host_activation.py work/new.cpr --track 1 --track 2 --out work/battery-activation.json
```

`--track` 可重复，采用 CPR 中所有乐器轨的 **1 基索引**，不含文件夹、音频轨和效果返回轨。对新建应发声的实例明确选择索引；省略时只检查默认 UID 或显式 UID 可识别的实例。它检查 instrument track 的保存属性，不覆盖其他 rack / MIDI 路由结构。

返回码 0 表示所选且已识别的实例均保存为 Active=1；2 表示存在停用、所选身份 / 属性未能确认，或没有识别到目标；1 表示文件读取或支持范围内的解析失败。报告写入全新文件；脚本不改源工程、不启用插件、不启动宿主、不计算文件哈希。它只报告保存的启用标记，不提供采样、音频输出或宿主实际播放结论。

## 按症状继续排查

| 症状或线索 | 接着核对的范围 |
| --- | --- |
| 新克隆实例无电平，kit / cell 可见 | 先读目标宿主 Active，再看实际 MIDI 接入与信号路径 |
| 只有个别鼓件无声 | 数字键号、通道、力度范围、触发条件、样本引用及 cell 输出 |
| 踩镲相互截断或开放镲不停 | 当前 Voice Group / Voices、触发条件与包络 |
| MIDI 很短，尾音仍很长 | 单次播放与 AHDSR / AHD 模式，按声音目标处理 |
| 总线或后台结果缺少部分鼓件 | Direct Out 与宿主已启用的输出、实际收集通道 |
| 后台有声，CPR 无声 | 将组件恢复证据与宿主 Active、mute / solo、总线路由分别核对 |

仅针对受影响轨道或声音继续检查。已有线索足够时完成相应修复；未知结构保留原文件并说明当前解析范围。需要界面或插件执行的步骤沿用会话授权，不因排查而扩大权限。
